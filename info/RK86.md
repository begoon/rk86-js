# Radio-86RK programmer's reference

A single reference for writing or reversing Intel 8080 code on the
Radio-86RK. The RK86's monitor ROM is not swappable — it defines
the hardware contract (variable slots, keyboard scan, video init,
tape format), so this document treats the monitor as an integral
part of the machine rather than a separate layer.

Sources:

- Monitor ROM: [begoon/rk86-monitor](https://github.com/begoon/rk86-monitor/blob/main/monitor.asm)
- Interactive viewer: <https://rk86.ru/monitor>
- Assembler: [asm8](https://github.com/begoon/asm8) — browser + CLI
  i8080 assembler. Same engine the emulator bundles as the asm8
  playground (toolbar "Ассемблер") and the terminal tool uses via
  `asm8080` on npm. Produces ready-to-load `.rk` files.

## Memory map

| Range       | Contents                                        |
|-------------|-------------------------------------------------|
| 0000h–75FFh | Free user RAM (30 KB on a 32 KB machine)        |
| 7600h–765Fh | Monitor variables ([see below](#monitor-variables-7600h765fh)) |
| 7660h–76CFh | Monitor stack (grows down from 76CFh)           |
| 76D0h–7FF4h | Video memory — 30 rows × 78 cols = 2340 B       |
| 8000h–8003h | PPI D20 (keyboard) — К580ВВ55                   |
| A000h–A003h | PPI D14 (tape / ROM-disk) — К580ВВ55            |
| C000h–C001h | CRT controller — К580ВГ75                       |
| E004h–E008h | DMA — К580ВТ57                                  |
| F000h       | ROM extension slot (`U` command jumps here)     |
| F800h–FFFFh | Monitor ROM (2 KB)                              |

`memory_top = 75FFh` is the documented upper bound of free user
memory; programs typically start with `lxi sp, 75FFh` (or any lower
address). The monitor itself runs with `SP = 76CFh`.

## Peripherals

### Keyboard (К580ВВ55 "D20" at 8000h)

| Addr  | Role                                                  |
|-------|-------------------------------------------------------|
| 8000h | Port A — row scan mask (output, active low)           |
| 8001h | Port B — column data (input, active low)              |
| 8002h | Port C — modifier keys + tape I/O                     |
| 8003h | Control word (monitor programs `8Bh` at cold start)   |

Port C bits (`8002h`, active low):

- bit 5 — SHIFT (СС)
- bit 6 — CTRL (УС)
- bit 7 — РУС/ЛАТ
- bits 0–3 — tape in/out and speaker

Matrix scan idiom:

```asm
    mvi  a, 0FDh        ; select row 1 (0 = active)
    sta  8000h
    lda  8001h          ; read columns
    cma                 ; 1 = pressed
```

Prefer the monitor's `getc` / `kbhit` / `scan_kbd` over raw matrix
reads — they handle autorepeat, РУС/ЛАТ, and debouncing.

### CRT controller (К580ВГ75 at C000h)

| Addr  | Role                                   |
|-------|----------------------------------------|
| C000h | Parameter / data register              |
| C001h | Command register (W) / status (R)      |

After a reset the screen is blank until the CRT is reprogrammed.
Call `F82Dh` (monitor `video`) to reinitialize it; cold start does
this automatically. The sequence emitted is:

| Write              | Decodes as                                               |
|--------------------|----------------------------------------------------------|
| `C001h ← 00h`      | **Reset** command — 4 parameter bytes follow on C000h    |
| `C000h ← 4Dh`      | SCN1: 78 characters per row (H=77, no row spacing)       |
| `C000h ← 1Dh`      | SCN2: 30 rows per frame (V=29, VR=0)                     |
| `C000h ← 99h`      | SCN3: 10 scan lines per char row, underline at line 9    |
| `C000h ← 93h`      | SCN4: line-counter mode + blinking full-block cursor     |
| `C001h ← 27h`      | **Start Display** command — DMA burst/spacing parameters |

Seeing the raw pattern `00 4D 1D 99 93 … 27` in a binary is almost
always a manual video reinit. Cursor blink is hardware-driven at
**500 ms** period.

#### Специальные управляющие символы 0xF0..0xFF

VG75 фильтрует поток DMA-байтов: старший hex-блок `0xF0..0xFF`
**не рисуется как глиф**, а интерпретируется как команда управления
выводом — Special Control Character. Битовая раскладка:

```text
1111 S B H U
     │ │ │ └─ U: Underline (подчёркивание для оставшейся части)
     │ │ └─── H: Highlight  (повышенная яркость / инверсия)
     │ └───── B: 0=Stop DMA для оставшейся части, 1=продолжать DMA
     └─────── S: 0=End of Row, 1=End of Screen (оборвать кадр)
```

| Code        | Действие                                                    |
|-------------|-------------------------------------------------------------|
| `F0`        | End of Row, продолжать DMA                                  |
| `F1`        | End of Row + Stop DMA до конца строки                       |
| `F2`/`F3`   | End of Row с подчёркиванием (Stop DMA — у `F3`)             |
| `F4`/`F5`   | End of Row с Highlight                                      |
| `F6`/`F7`   | End of Row с Highlight + Underline                          |
| `F8`–`FF`   | End of Screen — те же атрибуты, но обрывает **весь кадр**   |

При встрече такого байта VG75:

1. **Не выводит** глиф самого управляющего символа (текущая клетка
   остаётся пустой).
2. **Обрывает строку** (или весь кадр для `F8..FF`) — последующие
   клетки выводятся как пустые. На реальном железе с битом
   Stop-DMA контроллер вообще прекращает fetch'ить байты из
   видеопамяти, освобождая шину; у нас в эмуляторе это просто
   визуальная обрезка.
3. Обработчик внутри VG75 переключает атрибуты дисплея (highlight,
   underline) для оставшейся части — некоторые программы используют
   `F4..F7` как способ подсветить «концевик» строки без отдельной
   atomic-attribute-команды.

Типичное применение в РК86:

- **Динамическая ширина строки**. Программа программирует VG75 на
  78 столбцов, но реальный контент укладывается, скажем, в 64–68.
  Чтобы не выводить мусор справа от контента (особенно на TV с
  его overscan-обрезкой), программа кладёт `0xF1` сразу за
  последним полезным символом каждой строки. Получается чистая
  правая граница без необходимости явно пробельно-обнулять
  оставшиеся столбцы.
- **Маркер конца кадра**. `0xF8..0xFF` позволяет «выключить» нижнюю
  часть кадра — например, если видеоконтроллер запрограммирован на
  30 строк, а реально нужно показать 24, то `0xF8` в начале строки
  25 обрежет всё ниже без необходимости очищать память.

Программа squash by Дмитрий Иванов (2024) использует `0xF1` (и в
одной строке `0xF3`) ровно на col 68 каждой строки splash-битмапа.
На VG75 это даёт чистую видимую область шириной 68 столбцов; за её
пределами экран физически не рисуется.

**Замечание для эмулятора**: рендер обязан учитывать `0xF0..0xFF`
как спецкоды. Если читать байты напрямую и прогонять через charROM,
то `0xF1 & 0x7F = 0x71` даст глиф «Я», `0xF3 & 0x7F = 0x73` — «С», и
т. д. Получится красивая, но абсолютно неправильная вертикальная
колонка из Cyrillic-букв там, где должна быть пустая граница.

### DMA controller (К580ВТ57 at E000h)

Микросхема `i8257` (советский аналог — К580ВТ57, ИК57) — это
4-канальный контроллер DMA. Канал 2 в РК86 разведён на VG75 — он-то
и качает в видеоконтроллер байты экрана.

Каждый канал имеет два **16-битных** регистра:

- адрес начала (DMA address)
- счётчик слов (word count)

Но интерфейс к процессору — **8-битный** (по 8 линий данных D0..D7).
Чтобы записать 16-битное значение через 8-битную шину, оно подаётся
**двумя последовательными записями** в один и тот же порт: сначала
младший байт, потом старший.

Внутри микросхемы есть **один общий триггер первого/второго байта**
(first/second-byte flip-flop, F/F). Он работает как переключатель
«куда полетит следующий байт»:

- F/F = 0 → следующая запись идёт в **младшую половину** регистра,
  после чего F/F переключается в 1.
- F/F = 1 → следующая запись идёт в **старшую половину**, после
  чего F/F возвращается в 0 и регистр считается полностью загруженным.

F/F — **общий на всю микросхему**, не на каждый канал. Сбрасывается
он командой master-clear (запись `0x80` в управляющий регистр
`0xE008`).

Адресная карта в Радио-86РК:

```text
0xE000..0xE007 — адресные регистры каналов 0..3 (попарно: addr, count)
  0xE004 — канал 2: DMA address  ← база видеопамяти
  0xE005 — канал 2: word count   ← размер кадра в байтах
0xE008          — управляющий/статусный регистр
```

#### Стандартная последовательность инициализации

Программа, которая хочет настроить экран, делает:

```asm
MVI A, 80    \
STA  E008    /  master-clear, сбрасывает F/F в 0

MVI A, lo    \
STA  E004    |  F/F = 0 → low byte адреса. F/F переключается в 1.

MVI A, hi    \
STA  E004    |  F/F = 1 → high byte адреса. F/F возвращается в 0.

MVI A, lo    \
STA  E005    |  F/F = 0 → low byte размера. F/F переключается в 1.

MVI A, hi    \
STA  E005    |  F/F = 1 → high byte размера. F/F возвращается в 0.

MVI A, A4    \
STA  E008    /  enable канал 2
```

Эту последовательность эмулятор распознаёт по своей собственной
state-machine `ik57_e008_80_cmd`, которая идёт через состояния
`0 → 1 → 2 → 3 → 4 → 0` строго в этом порядке.

#### Быстрое переподключение DMA через F/F

После того как канал уже инициализирован, программа может перенастроить
адрес или размер на лету **без полного re-init цикла** — просто двумя
последовательными записями в `E004` (или `E005`), полагаясь на работу
F/F. Никакого master-clear (`E008 = 0x80`) перед этим не делается.

Конкретный пример из squash by Дмитрий Иванов (2024), по адресу
`0x0061` после инициализации splash-буфера на `0x134F`:

```asm
LXI  H, E004
MVI  M, BB    ; первая запись: low byte → промежуточный буфер
MVI  M, 07    ; вторая запись:  high byte → канал 2 переключается на 0x07BB
```

В реальном железе это работает так:

1. После предыдущей полной инициализации F/F **остался в состоянии 0**
   (естественное состояние после успешной 4-байтовой загрузки).
2. Первая запись `BB` → low byte адреса канала 2, F/F → 1.
3. Вторая запись `07` → high byte, F/F → 0.
4. Канал 2 теперь читает с `0x07BB`. DMA перенаправлено.

Эмулятор моделирует это через поле `ik57_ff` (общий F/F):

- Сбрасывается в 0 при `E008 = 0x80` (master clear).
- Переключается при каждой прямой записи в `E004` или `E005` (когда
  основная state-machine `ik57_e008_80_cmd` находится в состоянии 0,
  то есть первичная инициализация уже завершена).
- На «втором» байте (F/F = 1) применяет 16-битное значение через
  `screen.set_video_memory(...)` для `E004` или через обновление
  `video_memory_size` для `E005`, после чего сбрасывает F/F обратно
  в 0.

#### Тонкость, которую стоит держать в уме

F/F общий **на всю микросхему**, не на каждый канал и не на каждый
порт. То есть в реальном железе, если ты пишешь сначала в `E004`
(low), а потом в `E005`, второй порт получит **high byte** размера
(потому что F/F успел переключиться). Это редко используется
осознанно, но важно для отладки: смешанные подряд записи в разные
адресные порты делают невнятную смесь, ровно как на железе.

### Tape / ROM-disk PPI (К580ВВ55 "D14" at A000h)

| Addr  | Role                          |
|-------|-------------------------------|
| A000h | Port A — ROM-disk data        |
| A001h | Port B — ROM-disk addr low    |
| A002h | Port C — ROM-disk addr high   |
| A003h | Control word                  |

Most programs go through the monitor's `inpb` / `outb` / `inpblock` /
`outblock` entries rather than touching this PPI directly.

### Sound

The RK86 has no dedicated sound chip — the speaker is wired to
Port C bit 3 of the tape PPI (A002h). Tone is produced by toggling
that bit at the desired audio frequency. The emulator detects the
toggles on the 8080's interrupt-enable line (`EI`/`DI` pattern that
some programs use as a period marker) and synthesizes a square-wave
tone whose frequency is `1.78 MHz / (ticks_between_toggles × 2)`.

`putc 07h` ("beep") is a short tone produced this way; games drive
their own sound by timed `EI`/`DI` or bit-3 toggles in a delay loop.

## Keyboard matrix

Full 8×8 matrix (write `~(1<<row)` to `8000h`, read `8001h`, invert).
Cells name the **RK86 keycap**, not a PC key:

| Row | Bit 0     | Bit 1   | Bit 2   | Bit 3 | Bit 4 | Bit 5 | Bit 6 | Bit 7 |
|-----|-----------|---------|---------|-------|-------|-------|-------|-------|
| 0   | ↖ (home)  | СТР     | АР2     | Ф1    | Ф2    | Ф3    | Ф4    | —     |
| 1   | TAB       | `` ` `` | ПС/CR   | ЗБ/BS | ←     | ↑     | →     | ↓     |
| 2   | 0         | 1       | 2       | 3     | 4     | 5     | 6     | 7     |
| 3   | 8         | 9       | `*`/`:` | `;`   | `,`   | `-`   | `.`   | `/`   |
| 4   | `Ю`/`@`   | A/А     | B/Б     | C/Ц   | D/Д   | E/Е   | F/Ф   | G/Г   |
| 5   | H/Х       | I/И     | J/Й     | K/К   | L/Л   | M/М   | N/Н   | O/О   |
| 6   | P/П       | Q/Я     | R/Р     | S/С   | T/Т   | U/У   | V/Ж   | W/В   |
| 7   | X/Ь       | Y/Ы     | Z/З     | `[`   | `\`   | `]`   | `'`   | SPACE |

Row 0 is the non-alphanumeric "command" row. The real RK86 has only
**four function keys** (Ф1..Ф4); the rest of row 0 hosts ↖
(home-cursor), СТР (clear-screen) and АР2 (starts the monitor's
`ESC Y y x` cursor-positioning sequence). Letter cells show the two
glyphs sharing that keycap, `LAT/РУС`. Row 3 bit 2 and row 4 bit 0
are the two non-letter keycaps that swap glyphs with РУС/ЛАТ:
`*`↔`:` and `Ю`↔`@`.

Row 1 has the control-code keys; reading it with `FDh` on port A
gives back these codes:

| Bit | Key          | Code |
|-----|--------------|------|
| 0   | TAB          | 09h  |
| 1   | LF           | 0Ah  |
| 2   | CR (Enter)   | 0Dh  |
| 3   | DEL          | 7Fh  |
| 4   | Left arrow   | 08h  |
| 5   | Up arrow     | 19h  |
| 6   | Right arrow  | 18h  |
| 7   | Down arrow   | 1Ah  |

The emulator remaps modern PC keys onto this matrix — e.g. PC
`F5`..`F9` cover row 0's АР2 / Ф-keys / home / СТР, PC `F10`
toggles РУС/ЛАТ. Those are emulator conveniences, not RK86 hardware.

## Monitor ROM

The monitor ROM lives at F800h–FFFFh. Its jump table at F800h is
the stable ABI — call those slot addresses, not the `entry_*`
labels, since internal entry points can move between ROM revisions.

### Stack

Monitor sets `SP = 76CFh` (just below video memory at 76D0h). Stack
grows downward into the 7660h–76CEh area. User programs should use
the same stack or set SP to a safe address below 7600h.

### Monitor variables (7600h–765Fh)

| Addr  | Name              | Size | Meaning                                    |
|-------|-------------------|------|--------------------------------------------|
| 7600h | `cursor_addr`     | 2    | Video-RAM address of the cursor cell       |
| 7602h | `cursor_xy`       | 2    | `(Y,X)` — H=row, L=col                     |
| 7604h | `ap2_seq`         | 1    | Byte index in an АР2 escape sequence       |
| 7605h | `pressed_key`     | 1    | FFh = key held, 00h = released             |
| 7606h | `ruslat_flag`     | 1    | 00h = LAT, FFh = RUS                       |
| 7609h | `keyboard_repeat` | 2    | L = key code, H = autorepeat counter       |
| 760Dh | `temp_sp`         | 2    | Temp SP slot used by monitor commands      |
| 7614h | `pc_storage`      | 2    | Saved PC (G-command / breakpoint)          |
| 7616h | `hl_storage`      | 2    | Saved HL                                   |
| 7618h | `bc_storage`      | 2    | Saved BC                                   |
| 761Ah | `de_storage`      | 2    | Saved DE                                   |
| 761Ch | `sp_storage`      | 2    | Saved SP                                   |
| 761Eh | `af_storage`      | 2    | Saved A+PSW                                |
| 7623h | `stop_addr`       | 2    | Breakpoint address                         |
| 7625h | `stop_addr_value` | 1    | Original byte replaced by the breakpoint   |
| 7626h | `jump_to_go`      | 3    | `C3 xx xx` trampoline rewritten by `G`     |
| 7627h | `cmd_param_1`     | 2    | 1st parameter of the active command        |
| 7629h | `cmd_param_2`     | 2    | 2nd parameter                              |
| 762Bh | `cmd_param_3`     | 2    | 3rd parameter                              |
| 762Dh | `param_2_present` | 1    | FFh if the 2nd parameter was supplied      |
| 762Eh | `tape_polarity`   | 1    | Detected polarity of the tape input        |
| 762Fh | `tape_read_const` | 1    | Default `2Ah` (≈591 µs / bit)              |
| 7630h | `tape_write_const`| 1    | Default `1Dh` (≈406 µs / bit)              |
| 7631h | `memory_limit`    | 2    | Top-of-RAM reported by `getlim`            |
| 7633h | `kbd_buf`         | 32   | Keyboard ring buffer                       |
| 76CFh | `stack_bottom`    | —    | Monitor SP                                 |

`cursor_addr` at 7600h is handy for direct-to-video tricks: `lhld
7600h`, then write bytes through `(HL)`. `putc` updates it for you.

`jump_to_go` at 7626h is how user code is launched. The `G` command
writes the target into 7627h/7628h and does a plain `JMP 7626h`.
The slot doubles as the return-to-breakpoint vector: the `RST 6`
handler pushes flags/PC then returns through this trampoline so you
can resume with another `G`.

`ap2_seq` at 7604h tracks monitor escape-sequence state. Only
`ESC Y y x` is implemented: `1Bh` arms the sequence, the next byte
must be `Y`, and the two bytes after that set `row+20h`, `col+20h`.
Any other second byte aborts the sequence and is printed literally.

### Jump table (F800h)

| Addr  | Name     | In                                  | Out                                 | Notes                                |
|-------|----------|-------------------------------------|-------------------------------------|--------------------------------------|
| F800h | start    | —                                   | — (no return)                       | Cold start, reinitialize everything  |
| F803h | getc     | —                                   | A = key code                        | Blocks until a key is pressed        |
| F806h | inpb     | A = FFh for sync byte               | A = byte, CY on error               | Read one byte from tape              |
| F809h | putc     | C = character                       | —                                   | Print char; control codes handled    |
| F80Ch | outb     | C = byte                            | —                                   | Write one byte to tape               |
| F80Fh | —        | C = character                       | —                                   | Alias of `putc` (reserved slot)      |
| F812h | kbhit    | —                                   | A = key code or 0                   | Non-blocking keyboard check          |
| F815h | hexb     | A = byte                            | —                                   | Print A as two hex digits            |
| F818h | puts     | HL = string ptr                     | —                                   | Print zero-terminated string         |
| F81Bh | scan_kbd | —                                   | A = FFh/FEh/code                    | FFh = none, FEh = РУС/ЛАТ, else code |
| F81Eh | getxy    | —                                   | HL = `(y<<8)\|x`                    | Current cursor position              |
| F821h | curc     | —                                   | A = char under cursor               | Read character at cursor             |
| F824h | inpblock | HL = offset                         | HL = start, DE = end, BC = checksum | Read block from tape                 |
| F827h | outblock | HL = start, DE = end, BC = checksum | —                                   | Write block to tape                  |
| F82Ah | chksum   | HL = start, DE = end                | BC = checksum                       | Block checksum                       |
| F82Dh | video    | —                                   | —                                   | Reinitialize video controller        |
| F830h | getlim   | —                                   | HL = memory limit                   | Monitor's upper memory limit         |
| F833h | setlim   | HL = memory limit                   | —                                   | Change upper memory limit            |

Non-jump-table entry points worth knowing:

| Addr  | Name         | Notes                                             |
|-------|--------------|---------------------------------------------------|
| F836h | entry_start  | Cold start (banner + prompt)                      |
| F86Ch | prompt_loop  | `JMP F86Ch` = "exit back to monitor prompt"       |

ROM routines are not register-preserving — save anything you need
across a call. `putc` in particular touches PSW, B, D, H internally.

Typical end-of-program pattern:

```asm
    lxi h, msg
    call 0F818h      ; puts
    jmp 0F86Ch       ; back to monitor prompt

msg: db "hello, world", 0
```

### Monitor commands

The prompt accepts a single letter followed by up to three hex
arguments separated by spaces or commas, terminated by Enter (or `.`
to abort back to the prompt). `?` is echoed on a parse error.

| Cmd | Args                   | Action                                                         |
|-----|------------------------|----------------------------------------------------------------|
| `D` | `start,end`            | Dump memory as hex, 16 bytes per line                          |
| `L` | `start,end`            | List memory as text (printable chars; others shown as `.`)     |
| `F` | `start,end,byte`       | Fill `start..end` inclusive with `byte`                        |
| `S` | `start,end,byte`       | Search `start..end` for `byte`, report addresses               |
| `T` | `src_start,src_end,dst`| Transfer (copy) `src_start..src_end` to `dst`                  |
| `C` | `a_start,a_end,b_start`| Compare two blocks, report differences                         |
| `M` | `addr`                 | Modify memory — shows current byte, type new one or Enter/`.`  |
| `G` | `addr[,breakpoint]`    | Go — jump to `addr`, optionally set a breakpoint first         |
| `I` | `[offset]`             | Input block from tape; optional tape-constant `offset`         |
| `O` | `start,end[,const]`    | Output block `start..end` to tape; optional write-timing const |
| `R` | `start,end`            | Read block from ROM-disk (PPI D14 at A000h)                    |
| `X` | —                      | Print saved registers (after G or a breakpoint)                |
| `U` | —                      | Jump to `F000h` (ROM-extension slot)                           |

`G`'s breakpoint is implemented by patching `RST 6` (`F7h`) at the
target address; the original byte is saved in `stop_addr_value`
(7625h). When the breakpoint fires, the monitor saves all registers
into the 7614h–761Eh storage, restores the byte, and returns to the
prompt. `X` prints that saved state.

## Video memory

```text
rows 0..29  ×  78 columns per row  =  2340 bytes at 76D0h

video address(y, x) = 76D0h + y*78 + x
```

Each byte is a **character code**, not a pixel pattern — the ВГ75
fetches the glyph from the character-generator ROM. The default
text window used by the monitor covers **columns 8..71, rows 3..27**
(64 × 25). Its top-left is at `77C2h = 76D0h + 3*78 + 8`.

## Character set

One byte per cell, **KOI-7 N2** — the 7-bit Soviet standard that
KOI-8 is the 8-bit superset of. Russian uppercase lives at 60h–7Fh
(KOI-7 N2's Cyrillic half); the same letters appear at E0h–FFh in
KOI-8. Converting between them is a bit-7 flip: `koi8 = koi7 | 80h`.
On the RK86 those KOI-8 codes instead select the inverse-video copy
of the glyph, so strings are always written in the 60h–7Fh range.

## Tape

Programs almost always go through the monitor:

```asm
    lxi  h, start
    lxi  d, end
    call 0F827h        ; outblock - write HL..DE, BC=checksum out
    ...
    lxi  h, 0          ; 0 = use address from the block header
    call 0F824h        ; inpblock - read, CY set on checksum error
```

Low-level constants worth knowing:

| Value | Meaning                                     |
|-------|---------------------------------------------|
| E6h   | Sync byte — also a literal marker in files  |
| 2Ah   | Default read timing constant (≈591 µs/bit)  |
| 1Dh   | Default write timing constant (≈406 µs/bit) |

Bit framing — every bit is written as **two edges** on the tape
output line. The monitor emits the two edges roughly `1Dh` ticks
apart for `0` bits and with different spacing for `1` bits; the
receiver times edge-to-edge intervals and reconstructs the bit.
Bytes are 8 bits MSB-first. A block on tape has this structure:

```text
[256 × 00h lead-in]  E6h  start_hi start_lo  end_hi end_lo
                     [payload bytes]
                     E6h  sum_hi sum_lo
```

The 256-byte lead-in lets the receiver lock onto the bit timing
before the first `E6h` sync appears.

### DRAM-регенерация во время записи на ленту: трюк с `POP PSW`

В коде монитора по адресу `0xFC7B` (внутри routine'ы записи бита на
ленту) встречается такой цикл:

```asm
out_bit_loop2:
FC7B  F1          POP  PSW       ; «Регенерация ОЗУ» — комментарий из исходника
FC7C  05          DCR  B
FC7D  C2 7B FC    JNZ  out_bit_loop2
...
FC85  F9          SPHL           ; «Восстанавливаем SP и видео»
```

`POP PSW` здесь не работа со стеком — это **трюк для регенерации
динамической памяти**.

#### Почему RAM нужно регенерировать

РК86 на 32 КБ построен на динамической памяти К565РУ3 (16K×1, 16
микросхем). DRAM хранит бит как заряд на конденсаторе ячейки —
десятки фемтофарад, утечка через подзатвор и в подложку. Через ~2 мс
заряд деградирует настолько, что чтение становится ненадёжным.

Чтобы этого не произошло, **каждая строка DRAM должна быть
прочитана раз в ~2 мс**. У РУ3 это 128 строк (адресуются A0..A6 при
RAS-стробе). Любое обращение по адресу с битами A0..A6 = N
автоматически освежает строку N целиком (все 128 ячеек этой строки)
— это побочный эффект усилительного цикла внутри микросхемы.

#### Откуда регенерация берётся в обычном режиме

Регенерацией обычно занимается **видеоконтроллер VG75**. Через DMA
ИК57 он непрерывно читает видеопамять `0x76D0..0x7FF4` — 2340 байт
50 раз в секунду. 2340 > 128, поэтому за один кадр все 128 значений
A0..A6 проходятся много раз, **все строки DRAM освежаются**
автоматически как побочный эффект построения картинки.

Иначе говоря: **видео = бесплатная регенерация всей памяти**, потому
что строка DRAM «общая» для всего адресного пространства — A0..A6 = N
это одна и та же физическая строка независимо от того, в каком
128-байтном «листе» 16 КБ ты находишься.

#### Почему регенерации нет во время записи на ленту

Запись бита делается переключением бита 0 порта C (PPI `A002h`) с
**точно отмеренной** длительностью полупериодов: 1 — короткий,
0 — длинный. Тайминг должен быть стабильным, иначе магнитофон при
чтении не разберёт.

Если в это время работает DMA, она ворует у CPU непредсказуемое
число тактов (cycle-stealing — VG75 запрашивает шину раз в строку
растра). Тайминги полупериодов поплывут, лента запишется криво.

Поэтому первое, что делает routine записи на ленту — **выключает
DMA** (записью в `0xE008` управляющего слова, гасящего канал 2).
Сразу же исчезает и автоматическая регенерация — освежать DRAM
теперь некому. Если ничего не сделать, ~через 2 мс начнут «проседать»
произвольные ячейки, прежде всего там, где код записи на ленту
лежит сам — и процессор воткнётся в мусор.

Регенерацию обязан обеспечить сам процессор, доступом к памяти из
своего кода.

#### Что делает `POP PSW` за один такт

Опкод `F1` — одна байта. Делает три полезных вещи **одной
инструкцией за 10 тактов**:

1. **Читает байт** по адресу `(SP)`. Это обращение к памяти →
   DRAM-строка с адресом, соответствующим младшим битам `SP`,
   освежается.
2. **Читает второй байт** по адресу `(SP+1)`. Освежает ещё одну
   строку.
3. **Инкрементирует SP на 2**. Это «бесплатный» автоинкремент
   указателя — не нужно отдельной `INX` или `INR`.

Восстановленные в `A` и флаги при этом — **мусор**, и здесь это
никого не волнует: значения, которые `POP PSW` затирает, не нужны.
Аккумулятор в этот момент не используется (бит для ленты уже выведен
в порт `A002h` до начала задержки).

Одна инструкция = два чтения памяти + автоадвенс. Идеальный
«memory walker» для DRAM-регенерации.

#### Как это собирается в работающую регенерацию

Цикл задержки занимает 5 байт:

```asm
out_bit_loop2:
FC7B  F1          POP  PSW       ; 10 T  — читает (SP), (SP+1); SP += 2
FC7C  05          DCR  B         ;  5 T  — счётчик задержки--
FC7D  C2 7B FC    JNZ  out_bit_loop2 ; 10 T (taken)
```

Одна итерация = **25 T-состояний ≈ 14 мкс** на 1.78 МГц. За одну
итерацию SP продвигается на 2 байта, освежая 2 строки DRAM.

Чтобы SP пробежал ≥128 разных значений A0..A6, нужно сдвинуть SP на
≥128 байт = **≥64 итерации**. 64 × 14 мкс ≈ 900 мкс — полностью
укладывается в 2 мс окно регенерации. На длинном полупериоде `B`
обычно выставлен заметно больше 64, так что весь цикл регенерации
проходится несколько раз за один бит, с большим margin'ом против
разброса CPU-таймингов и разброса ёмкости конденсаторов в DRAM.

#### Что делает `SPHL` в `FC85`

Перед заходом в задержку и выключением DMA текущий стек был сохранён
в `HL` (где-то выше в routine'е). `SPHL` после конца цикла
**восстанавливает SP** в исходное положение, чтобы дальнейший
`CALL`/`RET` продолжал работать с настоящим стеком, а не с
прошедшимся через всю память «walker'ом».

То есть SP во время задержки буквально использовался как
**указатель-итератор для регенерации** — на семантику стека на это
время плюётся, потом честно возвращается обратно через `HL`.

#### Почему именно `POP PSW`, а не что-то другое

| Инструкция            | Длина | T-states | Чтения памяти | Авто-инкремент? | Минусы                                                            |
|-----------------------|------:|---------:|--------------:|:----------------|-------------------------------------------------------------------|
| `POP PSW`             |     1 |       10 |             2 | да (SP+=2)      | портит A, F (но они не нужны)                                     |
| `POP B/D/H`           |     1 |       10 |             2 | да (SP+=2)      | портит регистр пары — нужны для счётчика/управления               |
| `MOV A,M` + `INX H`   |     2 |     7+5  |             1 | да              | портит A, длиннее, медленнее, 1 строка/итерация                   |
| `LDA addr`            |     3 |       13 |  1 (+2 fetch) | нет (фикс.adr)  | один и тот же адрес = одна строка, регенерация не работает        |
| `LDAX D`/`LDAX B`     |     1 |        7 |             1 | нет             | нужна отдельная `INX`                                             |
| `NOP`                 |     1 |        4 |             0 | —               | вообще не освежает (только fetch той же строки)                   |

`POP PSW` выигрывает по совокупности: компактность, плотность
обращений к памяти, бесплатный авто-инкремент, портит регистр
которого жалко меньше всего. Другие `POP` тоже работают, но `B`,
`D`, `H` обычно заняты под счётчик / число бит / SP-копию, а
`PSW` — единственная пара, которую инженер мог себе позволить «слить».

#### Дополнительная деталь: instruction-fetch тоже регенерирует

Каждая выборка опкода — это тоже чтение памяти, тоже освежает
строку. CPU за итерацию фетчит 5 байт: `F1` по `FC7B`, `05` по
`FC7C`, `C2 7B FC` по `FC7D..FC7F`. Но это всегда **одни и те же 5
строк** (адреса кода фиксированы) — на них регенерация полная, на
остальных 123 — никакой. `POP PSW` именно для того и нужен, чтобы
**гулять по разным адресам** и тем самым прокатываться по всем
оставшимся строкам.

#### Где ещё встречается этот трюк

Идиома `POP rp` / `DCR ctr` / `JNZ` — **классика для cycle-perfect
I/O на машинах с DRAM**, где видеоконтроллер обычно занимается
регенерацией, а на время критичных по таймингу операций его
выключают. На РК86 такой код может появляться везде, где нужна
точность тайминга и не работает DMA — лента, реалтайм-звук через
бит-тогглинг A002h, точная развёртка спрайтов, синхронный обмен с
внешним устройством.

## File formats

Address fields are 2-byte **big-endian**; `end_addr` is the address
of the **last** byte (inclusive, not one-past-the-end). `payload`
is `end_addr − start_addr + 1` bytes of raw i8080 code/data —
identical to what you'd get from `.bin`. `checksum` is the monitor's
`chksum` routine (`F82Ah`) run over `start_addr..end_addr`, stored
big-endian.

Checksum algorithm — **not** a plain 16-bit sum. For a buffer of
`N` bytes `v[0..N-1]`:

```text
sum = 0
for i in 0..N-2:                       # every byte EXCEPT the last
    sum = (sum + v[i] + (v[i] << 8)) & 0xFFFF
# final byte folds into the low half only:
sum = (sum & 0xFF00) | ((sum + v[N-1]) & 0x00FF)
```

Equivalently: maintain two bytes `(hi, lo)`. For every byte except
the last, `lo += v[i]` and `hi += v[i] + carry_from_lo`. For the
last byte, only `lo` is updated, discarding any carry. This quirk
(last byte treated specially, checksum NOT a commutative sum) is
what makes the RK86 checksum distinguishable from a naive
accumulator when reversing.

| Extension     | Layout                                                                 |
|---------------|------------------------------------------------------------------------|
| `.bin`        | Raw payload only, no header or trailer.                                |
| `.rk`, `.rkr` | `start_hi start_lo end_hi end_lo` ‖ `payload` ‖ `E6 sum_hi sum_lo`     |
| `.pki`, `.gam`| `E6 start_hi start_lo end_hi end_lo` ‖ `payload` ‖ `E6 sum_hi sum_lo`  |

So `.pki` / `.gam` and `.rk` / `.rkr` differ only in the leading
sync byte: `.pki` / `.gam` repeat the `E6h` sync byte before the
address header, `.rk` / `.rkr` omit it. The trailing
`E6 sum_hi sum_lo` is the same in both.

Examples — a 3-byte payload `21 00 00` (`lxi h, 0`) at address
3000h, checksum `0021h`:

```text
.bin   21 00 00
.rk    30 00 30 02 | 21 00 00 | E6 00 21
.pki   E6 30 00 30 02 | 21 00 00 | E6 00 21
```

This is exactly the `.rk` tape-file format the playground emits.
Programs are loaded at the address encoded in the file header; the
asm8 `org` directive is what sets that address.

## Programming idioms

### Program skeleton

```asm
    org  3000h             ; any address in 0000h..75FFh
    lxi  sp, 75FFh         ; stack at the top of user RAM

    lxi  h, hello
    call 0F818h            ; puts
    jmp  0F86Ch            ; back to the monitor prompt

hello: db 'hi, world', 0Dh, 0Ah, 0
```

### Clear screen + print at (row, col)

```asm
    mvi  c, 1Fh            ; clear screen + home
    call 0F809h
    mvi  c, 1Bh            ; ESC
    call 0F809h
    mvi  c, 'Y'
    call 0F809h
    mvi  c, 3 + 20h        ; row 3
    call 0F809h
    mvi  c, 8 + 20h        ; col 8
    call 0F809h
    lxi  h, msg
    call 0F818h
```

A reusable `set_cursor` that patches an ESC-Y template in place
(preserves nothing by default) is how `docs/examples/dumped.asm`
does it.

### Read one key

```asm
wait:   call 0F803h         ; getc, blocks
        cpi  0Dh            ; Enter
        jz   done
        cpi  1Bh            ; ESC
        jz   abort
        ...
```

### Direct video write at current cursor

```asm
    lhld 7600h              ; HL = current cursor address
    mvi  m, 17h             ; 17h = full block
```

Direct writes bypass `putc`, so the monitor's own cursor tracking
stays in sync only if you follow up with a `putc` or an `ESC Y`
sequence.

### Exit back to the monitor

```asm
    jmp  0F86Ch             ; warm restart (keeps screen state)
    ; or
    jmp  0F800h             ; cold restart (reinitializes everything)
```

Pressing Ctrl-C during `getc` in a well-behaved program should route
to `0F800h` (the hard reset).

## Reversing cheat sheet

Patterns you will see over and over in RK86 binaries:

| Sequence                          | Meaning                        |
|-----------------------------------|--------------------------------|
| `31 FF 75`                        | `lxi sp, 75FFh` — stack init   |
| `CD 18 F8`                        | `call puts`                    |
| `CD 09 F8`                        | `call putc`                    |
| `CD 03 F8`                        | `call getc`                    |
| `CD 15 F8`                        | `call hexb` — print A as 2 hex |
| `C3 6C F8`                        | `jmp` to monitor prompt        |
| `0E 1F CD 09 F8`                  | clear screen                   |
| `0E 1B CD 09 F8 0E 59 CD 09 F8 …` | ESC-Y cursor positioning       |
| `2A 00 76`                        | `lhld 7600h` — cursor address  |
| `3A 06 76`                        | `lda 7606h` — РУС/ЛАТ flag     |
| Any `CPI 03h / JZ F800h`          | "Ctrl-C returns to monitor"    |
| `F1 05 C2 ?? ??`                  | DRAM-refresh delay loop        |

The `F1 05 C2 …` idiom decodes as `POP PSW` / `DCR B` / `JNZ self`
and isn't a stack operation — it's a **DRAM regenerator**. While
DMA is off (typically tape I/O or any cycle-perfect output), the CPU
walks `SP` through memory using the auto-increment of `POP` to
refresh DRAM rows on its own. See
[DRAM-регенерация во время записи на ленту](#dram-регенерация-во-время-записи-на-ленту-трюк-с-pop-psw)
for the full story.

Control-code checks on `getc` results (`CPI 08h / 18h / 19h / 1Ah`)
almost always indicate cursor-key handling.

Self-modifying `MVI A, nn` followed by a `STA ??+1` elsewhere is a
common idiom for storing a tiny amount of state inline — the dump
editor uses this to remember "mid-byte edit in progress" without
spending a RAM byte.

### i8080 opcode field layout (for manual disassembly)

Register index in `mov`, `mov r,r'`, `mvi`, arithmetic-with-r:

| r | 0 | 1 | 2 | 3 | 4 | 5 | 6     | 7 |
|---|---|---|---|---|---|---|-------|---|
|   | B | C | D | E | H | L | M=(HL)| A |

Register-**pair** index in `lxi rp`, `push`/`pop`, `dad`, `inx`/`dcx`,
`ldax`/`stax`:

| rp | 00 | 01 | 10 | 11 |
|----|----|----|----|----|
|    | BC | DE | HL | SP |

`push`/`pop` substitute `PSW` for the `11` slot (so `11` = SP for
`LXI`/`DAD`/`INX`/`DCX` but PSW for `PUSH`/`POP`).

### Undocumented/alias opcodes

The i8080 leaves several unused opcodes which behave as NOP but are
distinct in a disassembler's eyes — spotting them often means "this
byte is actually data, not code":

| Bytes                                          | Nominal behavior     |
|------------------------------------------------|----------------------|
| `08h`, `10h`, `18h`, `20h`, `28h`, `30h`, `38h`| NOP (alias)          |
| `CBh`                                          | JMP (alias of `C3h`) |
| `D9h`                                          | RET (alias of `C9h`) |
| `DDh`, `EDh`, `FDh`                            | CALL (alias of `CDh`)|

### Half-carry on AND (`ANA`) is unusual

Unlike ADD/SUB where half-carry is computed from bit 3 of
`(A + op)`, `ANA r` / `ANI n` sets HF from bit 3 of **`A | r`**
(logical OR of the operand and the accumulator). This is a real
i8080 quirk documented in the Intel 8080 Programmer's Manual —
code that branches on HF after an AND is relying on that formula,
not on the result.

### Russian strings typed as Latin

Old sources often store Cyrillic text by typing it on a Latin
keyboard and letting the 60h–7Fh range render the right glyphs. The
bytes look like gibberish in a hex dump but decode cleanly through
the Cyrillic row table above:

| Source bytes (as Latin) | Render on-screen       |
|-------------------------|------------------------|
| `pozdrawlq` s pobedoj`  | `ПОЗДРАВЛЯЮ С ПОБЕДОЙ` |
| `prigotowxtesx`         | `ПРИГОТОВЬТЕСЬ`        |

When you see a string that is almost-ASCII but peppered with
backticks, `q`, `x`, `w`, `{`, `|`, `}`, `~`, assume it's Russian
and translate via the 60h–7Fh mapping.
