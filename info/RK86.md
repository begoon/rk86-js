# Справочник программиста Радио-86РК

Единый справочник для написания и реверса кода Intel 8080 на
Радио-86РК. Мониторное ПЗУ РК86 несменяемое — оно определяет
аппаратный контракт (слоты переменных, опрос клавиатуры,
инициализацию видео, формат ленты), поэтому в этом документе
монитор рассматривается как неотъемлемая часть машины, а не
отдельный слой.

Источники:

- Мониторное ПЗУ: [begoon/rk86-monitor](https://github.com/begoon/rk86-monitor/blob/main/monitor.asm)
- Интерактивный просмотрщик: <https://rk86.ru/monitor>
- Ассемблер: [asm8](https://github.com/begoon/asm8) — браузерный
  и CLI ассемблер i8080. Тот же движок, что эмулятор поставляет
  как asm8-плейграунд (кнопка тулбара «Ассемблер»), а
  терминальный инструмент использует через `asm8080` в npm.
  Производит готовые к загрузке `.rk`-файлы.

## Карта памяти

| Диапазон    | Содержимое                                                        |
| ----------- | ----------------------------------------------------------------- |
| 0000h–75FFh | Свободное пользовательское ОЗУ (30 КБ на 32-КБ машине)            |
| 7600h–765Fh | Переменные монитора ([см. ниже](#переменные-монитора-7600h765fh)) |
| 7660h–76CFh | Стек монитора (растёт вниз от 76CFh)                              |
| 76D0h–7FF4h | Видеопамять — 30 строк × 78 колонок = 2340 Б                      |
| 8000h–8003h | PPI D20 (клавиатура) — К580ВВ55                                   |
| A000h–A003h | PPI D14 (лента / ROM-disk) — К580ВВ55                             |
| C000h–C001h | Контроллер CRT — К580ВГ75                                         |
| E004h–E008h | DMA — К580ВТ57                                                    |
| F000h       | Слот расширения ПЗУ (команда `U` прыгает сюда)                    |
| F800h–FFFFh | Мониторное ПЗУ (2 КБ)                                             |

`memory_top = 75FFh` — документированная верхняя граница свободной
пользовательской памяти; программы обычно начинаются с
`lxi sp, 75FFh` (или любого адреса ниже). Сам монитор работает с
`SP = 76CFh`.

### Дешифрация адресов и зеркалирование периферии

В РК86 дешифрация периферии — это **К555ИД7 (74LS138)**, 3-в-8.
На вход декодера подаются три старших бита процессорного адреса:
**A13, A14, A15**. Один из 8 chip-select сигналов активирует
соответствующий чип:

| `A15 A14 A13` | Диапазон    | Что выбирается                  |
| ------------- | ----------- | ------------------------------- |
| `000`         | `0000-1FFF` | RAM банк 0, нижние 8K           |
| `001`         | `2000-3FFF` | RAM банк 0, верхние 8K          |
| `010`         | `4000-5FFF` | RAM банк 1, нижние 8K           |
| `011`         | `6000-7FFF` | RAM банк 1, верхние 8K          |
| `100`         | `8000-9FFF` | PPI ВВ55 «D20» (клавиатура)     |
| `101`         | `A000-BFFF` | PPI ВВ55 «D14» (лента/ROM-disk) |
| `110`         | `C000-DFFF` | VG75 (CRT)                      |
| `111`         | `E000-FFFF` | ВТ57 / ROM extension / монитор  |

Главное следствие: **chip-select работает с гранулярностью 8 КБ**.
Когда A15..A13 = `110`, активируется VG75 на ВЕСЬ диапазон от
`C000` до `DFFF`. Бит **A12 для chip-select don't-care**.

На сами периферийные чипы из CPU-адреса заводятся только младшие
биты — столько, сколько у чипа адресных входов:

| Чип        | Адресные входы | Регистров | Биты от CPU    |
| ---------- | -------------- | --------- | -------------- |
| ВВ55 (PPI) | A0, A1         | 4         | A0, A1         |
| ВГ75 (CRT) | A0 (R/S)       | 2         | A0             |
| ВТ57 (DMA) | A0..A3         | 16        | A0..A3 (часть) |

Остальные биты адреса (A1..A12 для VG75, A2..A12 для PPI, A4..A12
для DMA) **не доходят до чипа** — они для него don't-care. Внутри
своего 8K-диапазона каждая регистровая пара/группа повторяется
многократно как **зеркало**:

| Реальный адрес | Зеркала во всём 8K-диапазоне                     |
| -------------- | ------------------------------------------------ |
| `8000` (PA)    | `8004`, `8008`, ..., `87FC`, `8800`, ..., `9FFC` |
| `8001` (PB)    | `8005`, ..., `9FFD`                              |
| `8002` (PC)    | `8006`, ..., `9FFE`                              |
| `8003` (CTL)   | `8007`, ..., `9FFF`                              |
| `C000` (data)  | `C002`, ..., `CFFE`, `D000`, ..., `DFFE`         |
| `C001` (cmd)   | `C003`, ..., `DFFF`                              |

Например, **`D001` ≡ `C001`** — это статусный регистр VG75 (тот же
самый бит 5 = VRTC, бит 4 = light pen). Программа, читающая из
`D001`, на реальном железе получит то же самое, что и из `C001`.

ROM-зона (`F000-F7FF` extension slot и `F800-FFFF` монитор) — это
особый случай: chip-select для них тоже `111` (как у ВТ57), но
дальше идёт **второй уровень дешифрации** — чтения проходят на ROM,
записи в `E000-EFFF` идут на ВТ57. Так что `F800-FFFF` НЕ зеркалит
ВТ57; они разделены младшими битами.

#### В эмуляторе

Маска `addr & 0xEFFF` (только A12 don't-care) **недостаточна** —
она покрывает A12, но игнорирует остальные don't-care биты внутри
8K-зоны. Поэтому используются **per-peripheral маски**, точно
повторяющие количество адресных входов каждого чипа:

```js
const ppi_reg  = addr & 0xE003;  // PPI: A0..A1, остальные mirrored
const vg75_reg = addr & 0xE001;  // VG75: A0, остальные mirrored
const vt57_reg = addr & 0xE00F;  // VT57: A0..A3, остальные mirrored
```

Сравнение: что пропускалось при старой маске и теперь проходит:

| Адрес  | Старая маска `& 0xEFFF` | Новая (per-peripheral) | Назначение               |
| ------ | ----------------------- | ---------------------- | ------------------------ |
| `D001` | `C001` ✓                | `C001` ✓               | VG75 cmd/status          |
| `D002` | `C002` ✗                | `C000` ✓               | VG75 data (mirror, A0=0) |
| `D003` | `C003` ✗                | `C001` ✓               | VG75 cmd/status (mirror) |
| `9001` | `8001` ✓                | `8001` ✓               | keyboard scan            |
| `9402` | `8402` ✗                | `8002` ✓               | keyboard PC mirror       |
| `B003` | `A003` ✓                | `A003` ✓               | tape PPI control         |
| `E008` | `E008` ✓                | `E008` ✓               | VT57 mode                |
| `E018` | `E018` ✗                | `E008` ✓               | VT57 mode mirror         |
| `F808` | `E808` ✗                | `E008` ✓               | VT57 mode (F-range!)     |

`F808 → E008` особенно важен: некоторые программы (rise.rkr,
например) программируют DMA через **`F808/F804/F805` вместо
`E008/E004/E005`**. Это работает на железе, потому что:

- chip-select VT57 — это `A15..A13 = 111` (диапазон `E000-FFFF`).
- Внутри этого диапазона A4..A12 для чипа don't-care.
- Хотя A12 = 1 уводит в ROM-зону для **чтения**, **записи**
  всё ещё активизируют VT57 (на железе ROM is read-only — write
  decode ignores it; чип VT57 принимает запись).

Эмулятор моделирует это разделением:

- `if (addr < 0xF800) buf[addr] = byte` — RAM update, но **не для
  ROM** (защищает загруженный монитор от затирания).
- Periphery handlers вызываются **всегда**, независимо от того,
  попал ли адрес в ROM-зону. F-range writes к VT57-зеркалам
  (например, `F808`) корректно дёргают DMA-state-machine.
- ROM reads в `F800-FFFF` не задеваются — read-handlers per-
  peripheral масок не дают им матчей, чтение проваливается на
  `return buf[addr]`, возвращая корректный ROM-байт.

Зеркалирование к мониторному ROM (например, `FFFE` ≡ `EFFE`)
не реализовано как peripheral, потому что в реальном железе там
ничего интересного — это просто ROM-байты в адресной зоне,
выбранной chip-select 111 + A12=1 (ROM-decode).

## Периферия

### Клавиатура (К580ВВ55 «D20» по адресу 8000h)

| Адрес | Назначение                                                  |
| ----- | ----------------------------------------------------------- |
| 8000h | Порт A — маска опроса строк (вывод, активный низкий)        |
| 8001h | Порт B — данные столбцов (ввод, активный низкий)            |
| 8002h | Порт C — модификаторы + ввод-вывод ленты                    |
| 8003h | Управляющее слово (монитор пишет `8Bh` при холодном старте) |

Биты порта C (`8002h`, активные низкие):

- бит 5 — SHIFT (СС)
- бит 6 — CTRL (УС)
- бит 7 — РУС/ЛАТ
- биты 0–3 — вход/выход ленты и динамик

Идиома опроса матрицы:

```asm
    mvi  a, 0FDh        ; выбор строки 1 (0 = активна)
    sta  8000h
    lda  8001h          ; чтение столбцов
    cma                 ; 1 = нажато
```

Предпочитайте мониторные `getc` / `kbhit` / `scan_kbd` прямому
чтению матрицы — они обрабатывают автоповтор, РУС/ЛАТ и дребезг.

### Контроллер CRT (К580ВГ75 по адресу C000h)

| Адрес | Назначение                      |
| ----- | ------------------------------- |
| C000h | Регистр параметров / данных     |
| C001h | Регистр команд (W) / статус (R) |

После сброса экран пуст до перепрограммирования CRT. Вызов `F82Dh`
(мониторный `video`) переинициализирует его; холодный старт делает
это автоматически. Эмитируется такая последовательность:

| Запись        | Расшифровка                                                      |
| ------------- | ---------------------------------------------------------------- |
| `C001h ← 00h` | Команда **Reset** — далее на C000h следуют 4 байта параметров    |
| `C000h ← 4Dh` | SCN1: 78 символов в строке (H=77, без межстрочного интервала)    |
| `C000h ← 1Dh` | SCN2: 30 строк в кадре (V=29, VR=0)                              |
| `C000h ← 99h` | SCN3: 10 строк развёртки на знакоместо, подчёркивание на линии 9 |
| `C000h ← 93h` | SCN4: режим transparent FA (бит 6=0), мигающий курсор            |
| `C001h ← 27h` | Команда **Start Display** — параметры DMA burst/spacing          |

Бит 6 SCN4 — это **флаг F (Field Attribute)**: `0` = режим
transparent (FA-клетка заполняется дополнительным DMA-байтом из
16-байтового FIFO чипа; поведение чипа по умолчанию и то, с чем
поставляется vanilla `mon32.bin`), `1` = visible (FA-клетка
обнуляется, FA-байт занимает ровно одну клетку как пробел). Мигание
курсора выполняется аппаратно с периодом **500 мс**.

В репозитории поставляются **два** мониторных ПЗУ:

- **`kit/static/files/mon32.bin`** — vanilla, байт 4 = `93h`
  (transparent). По умолчанию загружается и `boot.ts` (web), и
  встроенным `MON32_B64` в `terminal.ts`. Используйте его для
  программ, написанных под исходное программирование чипа,
  например `tree2025.rk` с её layout-ом упакованного цвета
  `[FA][char]…`.
- **`kit/static/files/mon32-color.bin`** — патченный, байт 4 = `D3h`
  (visible). Используйте его для цветного режима, который
  рассчитан на visible-mode программирование чипа (dizzy75, squash,
  boulder, rise, piton, …) — эти программы раскладывают экранную
  RAM как `[FA][char][zeros]…` и полагаются на то, что FA-клетка
  пустая.
  Web: `?monitor=mon32-color.bin`.
  Terminal: `-m static/files/mon32-color.bin`.

Наш `memory.ts` захватывает бит F в `screen.transparent_attr` при
каждом сбросе i8275, а `renderer.ts` (canvas) /
`TerminalRenderer.update()` (terminal) ветвится между transparent-
путём с FIFO и visible-путём с пустой клеткой соответственно.
Смена ROM в runtime → флаг чипа переключается → рендер-путь
следует за ним.

#### Классификация байтов из видеопамяти

VG75 (i8275) **классифицирует каждый байт** из DMA-потока по
старшим битам:

| Битовая раскладка | Диапазон  | Тип                                     |
| ----------------- | --------- | --------------------------------------- |
| `0xxxxxxx`        | `00`-`7F` | Normal character (7-битный код символа) |
| `10xxxxxx`        | `80`-`BF` | Field Attribute (цвет/highlight/blink)  |
| `11xxxxxx`, <`F0` | `C0`-`EF` | Character Attribute (line graphics)     |
| `1111xxxx`        | `F0`-`FF` | Special Control (end of row/screen)     |

##### Field Attribute (`80`-`BF`)

Байт защелкивает атрибуты, эмитятся на пинах чипа и держатся **до
следующего FA-байта (или VRTC)**. Битовая раскладка (Intel 8275
datasheet, MAME `i8275.cpp`, Emu80 `Crt8275.cpp`):

```text
bit 7  6  5  4  3  2  1  0
    1  0  U  R  GG GG B  H
          │  │  │  │  │  └── H   = Highlight (HLGT pin)
          │  │  └──┴──┴───── GG  = GPA1 (bit 3), GPA0 (bit 2)
          │  │     B   ────  B   = Blink (32-frame, drives VSP)
          │  └──────────────  R   = Reverse (RVV pin)
          └─────────────────  U   = Underline (LTEN @ underline scanline)
```

В РК86 пины разведены **по схеме 86rk.ru** (инвертированная — установленный
бит **выключает** соответствующий цветовой канал), что означает «default
attribute = white text on black»:

```js
// 86rk august.video_86rk.js
r = ch.hglt ? 0x00 : 0xFF   // bit 0 set → red OFF
g = ch.gpa1 ? 0x00 : 0xFF   // bit 3 set → green OFF
b = ch.gpa0 ? 0x00 : 0xFF   // bit 2 set → blue OFF
```

С `color_index = (H << 2) | (G1 << 1) | G0`:

| index | bits set | цвет    | пример байта |
| ----- | -------- | ------- | ------------ |
| 0     | (none)   | white   | `80`         |
| 1     | G0       | yellow  | `84`         |
| 2     | G1       | magenta | `88`         |
| 3     | G0+G1    | red     | `8C`         |
| 4     | H        | cyan    | `81`         |
| 5     | H+G0     | green   | `85`         |
| 6     | H+G1     | blue    | `89`         |
| 7     | H+G0+G1  | black   | `8D`         |

(Index 7 рендерится чёрным — символы с этим атрибутом фактически
**невидимы** на чёрном фоне. Используется как «hide», например в
`dizzy75.rkr` строка под «THEDARK DESIGN».)

Альтернативные схемы — Tolkalin (Радиолюбитель 04/1992,
`GPA0=R, GPA1=G, HLGT=B`, default = чёрный, biт включает канал) и
Emu80 RCM_COLOR1 (3-way rotation `GPA0=Green, GPA1=Blue, HLGT=Red`,
default = light gray) — отличаются от 86rk-варианта на уровне
RGB-разводки, но **формат байта одинаковый**. Apogee БК-01Ц меняет
GPA0↔GPA1 местами на уровне платы, что даёт ещё одну несовместимость.

##### Field-attribute display modes (visible vs transparent)

Бит F SCN4 (см. таблицу выше) переключает чип между двумя режимами
обработки FA-байтов:

- **Visible (F=1)** — FA-байт занимает одну ячейку, отображаемую
  как blank (chip принудительно поднимает VSP для этой клетки).
  Простой случай: эмулятор fetch'ит ровно `width` байт на строку,
  на FA-байтах — пустая клетка, цвет защёлкнут на следующие.
- **Transparent (F=0)** — FA-байт **не занимает** клетку: чип
  тянет следующий байт из 16-байтового FIFO (заполняемого
  доп. DMA-burst'ами) и рисует **его** в этой клетке.
  Программы типа `tree2025.rk` пишут видеопамять как
  `[FA][char][FA][char]…` — пары схлопываются в одну видимую
  клетку, что и даёт плотно упакованную раскраску.
  В нашей реализации (`renderer.ts` transparent-path):
  - читаем до `width + K` исходных байт за строку (K = число FA);
  - для каждой FA-клетки кладём метку и сохраняем
    непосредственно следующий байт в FIFO;
  - при выводе FA-клетки заменяем символ на FIFO[i++];
  - F1/F2 останавливают DMA посередине строки, оставшиеся клетки
    рисуем blank.

##### Latch carry-over и render rules

Защёлкнутые атрибуты (color + blink + R + U) **сохраняются между
строками** — сбрасываются только на VRTC (начало кадра). Программы
полагаются на это: например `dizzy75.rkr` на строке 8 вешает
«невидимый» атрибут (`F8D`, all-bits set → черный в 86rk-палитре),
а строка 9 ниже идёт без своих FA — её plain-`76h` символы
рендерятся всё ещё в защёлкнутом «black», т.е. невидимыми.

Никакого one-cell offset (Emu80 RCM_COLOR1 `m_hgltOffset` /
`m_gpaOffset`) мы **не применяем**: каждая клетка рисуется в своём
текущем защёлкнутом цвете (FA-байт сначала захватывает старый цвет
для собственной blank-клетки, потом обновляет latch для следующих).
Поведение совпадает с 86rk.ru — Emu80 в его специфическом
RCM_COLOR1 mode сдвигает цветовые границы на одну клетку влево; мы
этого не делаем, чтобы соответствовать тому, как РК-программы
выглядят в 86rk.ru.

Blink: бит B (бит 1 FA-байта) включает мигание для последующих
ячеек до следующего FA. Чип на реальном железе тогглит VSP на
1/32 кадра — мы аппроксимируем это wall-clock'ом 320 ms (~1.5 Hz).

##### Character Attribute (`C0`-`EF`)

Генерирует line-graphics символы (рамки, углы) средствами самого
VG75 без обращения к charROM. **РК86 эту фичу не использует** —
charROM К573РФ1 содержит 128 глифов, прошивка не эмитит байты
≥ `C0` в видеопамять. Эмулятор рисует такие ячейки как пустые.

##### Special Control (`F0`-`FF`)

См. ниже — управление потоком DMA (end-of-row, end-of-screen).

#### Специальные управляющие символы 0xF0..0xFF

VG75 фильтрует поток DMA-байтов: старший hex-блок `0xF0..0xFF`
**не рисуется как глиф**, а интерпретируется как команда управления
выводом — Special Control Character. Битовая раскладка:

```text
1111 S B H U
     │ │ │ └─ U: Underline (подчёркивание для оставшейся части)
     │ │ └─── H: Highlight  (повышенная яркость / инверсия)
     │ └───── B: 0=Stop DMA для оставшейся части, 1=продолжать DMA
     └─────── S: 0=End of Row, 1=End of Screen (оборвать кадр)
```

| Code      | Действие                                                  |
| --------- | --------------------------------------------------------- |
| `F0`      | End of Row, продолжать DMA                                |
| `F1`      | End of Row + Stop DMA до конца строки                     |
| `F2`/`F3` | End of Row с подчёркиванием (Stop DMA — у `F3`)           |
| `F4`/`F5` | End of Row с Highlight                                    |
| `F6`/`F7` | End of Row с Highlight + Underline                        |
| `F8`–`FF` | End of Screen — те же атрибуты, но обрывает **весь кадр** |

При встрече такого байта VG75:

1. **Не выводит** глиф самого управляющего символа (текущая клетка
   остаётся пустой).
2. **Обрывает строку** (или весь кадр для `F8..FF`) — последующие
   клетки выводятся как пустые. На реальном железе с битом
   Stop-DMA контроллер вообще прекращает fetch'ить байты из
   видеопамяти, освобождая шину; у нас в эмуляторе это просто
   визуальная обрезка.
3. Обработчик внутри VG75 переключает атрибуты дисплея (highlight,
   underline) для оставшейся части — некоторые программы используют
   `F4..F7` как способ подсветить «концевик» строки без отдельной
   atomic-attribute-команды.

Типичное применение в РК86:

- **Динамическая ширина строки**. Программа программирует VG75 на
  78 столбцов, но реальный контент укладывается, скажем, в 64–68.
  Чтобы не выводить мусор справа от контента (особенно на TV с
  его overscan-обрезкой), программа кладёт `0xF1` сразу за
  последним полезным символом каждой строки. Получается чистая
  правая граница без необходимости явно пробельно-обнулять
  оставшиеся столбцы.
- **Маркер конца кадра**. `0xF8..0xFF` позволяет «выключить» нижнюю
  часть кадра — например, если видеоконтроллер запрограммирован на
  30 строк, а реально нужно показать 24, то `0xF8` в начале строки
  25 обрежет всё ниже без необходимости очищать память.

Программа squash by Дмитрий Иванов (2024) использует `0xF1` (и в
одной строке `0xF3`) ровно на col 68 каждой строки splash-битмапа.
На VG75 это даёт чистую видимую область шириной 68 столбцов; за её
пределами экран физически не рисуется.

**Замечание для эмулятора**: рендер обязан учитывать `0xF0..0xFF`
как спецкоды. Если читать байты напрямую и прогонять через charROM,
то `0xF1 & 0x7F = 0x71` даст глиф «Я», `0xF3 & 0x7F = 0x73` — «С», и
т. д. Получится красивая, но абсолютно неправильная вертикальная
колонка из Cyrillic-букв там, где должна быть пустая граница.

### DMA controller (К580ВТ57 at E000h)

Микросхема `i8257` (советский аналог — К580ВТ57, ИК57) — это
4-канальный контроллер DMA. Канал 2 в РК86 разведён на VG75 — он-то
и качает в видеоконтроллер байты экрана.

Каждый канал имеет два **16-битных** регистра:

- адрес начала (DMA address)
- счётчик слов (word count)

Но интерфейс к процессору — **8-битный** (по 8 линий данных D0..D7).
Чтобы записать 16-битное значение через 8-битную шину, оно подаётся
**двумя последовательными записями** в один и тот же порт: сначала
младший байт, потом старший.

Внутри микросхемы есть **один общий триггер первого/второго байта**
(first/second-byte flip-flop, F/F). Он работает как переключатель
«куда полетит следующий байт»:

- F/F = 0 → следующая запись идёт в **младшую половину** регистра,
  после чего F/F переключается в 1.
- F/F = 1 → следующая запись идёт в **старшую половину**, после
  чего F/F возвращается в 0 и регистр считается полностью загруженным.

F/F — **общий на всю микросхему**, не на каждый канал. Сбрасывается
он командой master-clear (запись `0x80` в управляющий регистр
`0xE008`).

Адресная карта в Радио-86РК:

```text
0xE000..0xE007 — адресные регистры каналов 0..3 (попарно: addr, count)
  0xE004 — канал 2: DMA address  ← база видеопамяти
  0xE005 — канал 2: word count   ← размер кадра в байтах
0xE008          — управляющий/статусный регистр
```

#### Стандартная последовательность инициализации

Программа, которая хочет настроить экран, делает:

```asm
MVI A, 80    \
STA  E008    /  master-clear, сбрасывает F/F в 0

MVI A, lo    \
STA  E004    |  F/F = 0 → low byte адреса. F/F переключается в 1.

MVI A, hi    \
STA  E004    |  F/F = 1 → high byte адреса. F/F возвращается в 0.

MVI A, lo    \
STA  E005    |  F/F = 0 → low byte размера. F/F переключается в 1.

MVI A, hi    \
STA  E005    |  F/F = 1 → high byte размера. F/F возвращается в 0.

MVI A, A4    \
STA  E008    /  enable канал 2
```

Эту последовательность эмулятор распознаёт по своей собственной
state-machine `ik57_e008_80_cmd`, которая идёт через состояния
`0 → 1 → 2 → 3 → 4 → 0` строго в этом порядке.

#### Быстрое переподключение DMA через F/F

После того как канал уже инициализирован, программа может перенастроить
адрес или размер на лету **без полного re-init цикла** — просто двумя
последовательными записями в `E004` (или `E005`), полагаясь на работу
F/F. Никакого master-clear (`E008 = 0x80`) перед этим не делается.

Конкретный пример из squash by Дмитрий Иванов (2024), по адресу
`0x0061` после инициализации splash-буфера на `0x134F`:

```asm
LXI  H, E004
MVI  M, BB    ; первая запись: low byte → промежуточный буфер
MVI  M, 07    ; вторая запись:  high byte → канал 2 переключается на 0x07BB
```

В реальном железе это работает так:

1. После предыдущей полной инициализации F/F **остался в состоянии 0**
   (естественное состояние после успешной 4-байтовой загрузки).
2. Первая запись `BB` → low byte адреса канала 2, F/F → 1.
3. Вторая запись `07` → high byte, F/F → 0.
4. Канал 2 теперь читает с `0x07BB`. DMA перенаправлено.

Эмулятор моделирует это через поле `ik57_ff` (общий F/F):

- Сбрасывается в 0 при `E008 = 0x80` (master clear).
- Переключается при каждой прямой записи в `E004` или `E005` (когда
  основная state-machine `ik57_e008_80_cmd` находится в состоянии 0,
  то есть первичная инициализация уже завершена).
- На «втором» байте (F/F = 1) применяет 16-битное значение через
  `screen.set_video_memory(...)` для `E004` или через обновление
  `video_memory_size` для `E005`, после чего сбрасывает F/F обратно
  в 0.

#### Тонкость, которую стоит держать в уме

F/F общий **на всю микросхему**, не на каждый канал и не на каждый
порт. То есть в реальном железе, если ты пишешь сначала в `E004`
(low), а потом в `E005`, второй порт получит **high byte** размера
(потому что F/F успел переключиться). Это редко используется
осознанно, но важно для отладки: смешанные подряд записи в разные
адресные порты делают невнятную смесь, ровно как на железе.

### PPI ленты / ROM-disk (К580ВВ55 «D14» по адресу A000h)

| Адрес | Назначение                            |
| ----- | ------------------------------------- |
| A000h | Порт A — данные ROM-disk              |
| A001h | Порт B — младший байт адреса ROM-disk |
| A002h | Порт C — старший байт адреса ROM-disk |
| A003h | Управляющее слово                     |

Большинство программ работают через мониторные точки входа `inpb` /
`outb` / `inpblock` / `outblock`, а не напрямую с этим PPI.

### Звук

В РК86 нет выделенной звуковой микросхемы — динамик подключён к
биту 3 порта C ленточного PPI (A002h). Тон создаётся переключением
этого бита с нужной звуковой частотой. Эмулятор детектирует
переключения на линии разрешения прерываний 8080 (паттерн `EI`/`DI`,
который некоторые программы используют как маркер периода) и
синтезирует прямоугольный тон с частотой
`1.78 МГц / (тиков_между_переключениями × 2)`.

`putc 07h` («бип») — короткий тон, создаваемый этим способом; игры
управляют своим звуком через тайминговые `EI`/`DI` или переключения
бита 3 в задержечном цикле.

## Матрица клавиатуры

Полная матрица 8×8 (запись `~(1<<row)` в `8000h`, чтение `8001h`,
инверсия). Ячейки именуют **клавишу РК86**, а не клавишу PC:

| Row | Bit 0    | Bit 1   | Bit 2   | Bit 3 | Bit 4 | Bit 5 | Bit 6 | Bit 7 |
| --- | -------- | ------- | ------- | ----- | ----- | ----- | ----- | ----- |
| 0   | ↖ (home) | СТР     | АР2     | Ф1    | Ф2    | Ф3    | Ф4    | —     |
| 1   | TAB      | `` ` `` | ПС/CR   | ЗБ/BS | ←     | ↑     | →     | ↓     |
| 2   | 0        | 1       | 2       | 3     | 4     | 5     | 6     | 7     |
| 3   | 8        | 9       | `*`/`:` | `;`   | `,`   | `-`   | `.`   | `/`   |
| 4   | `Ю`/`@`  | A/А     | B/Б     | C/Ц   | D/Д   | E/Е   | F/Ф   | G/Г   |
| 5   | H/Х      | I/И     | J/Й     | K/К   | L/Л   | M/М   | N/Н   | O/О   |
| 6   | P/П      | Q/Я     | R/Р     | S/С   | T/Т   | U/У   | V/Ж   | W/В   |
| 7   | X/Ь      | Y/Ы     | Z/З     | `[`   | `\`   | `]`   | `'`   | SPACE |

Строка 0 — это «командная» строка без букв и цифр. На реальной
РК86 только **четыре функциональные клавиши** (Ф1..Ф4); остальное в
строке 0 — это ↖ (home-cursor), СТР (clear-screen) и АР2 (запуск
мониторной escape-последовательности `ESC Y y x` для позиционирования
курсора). Буквенные ячейки показывают два глифа на одной клавише,
`LAT/РУС`. Бит 2 строки 3 и бит 0 строки 4 — это две небуквенные
клавиши, которые тоже меняют глифы по РУС/ЛАТ: `*`↔`:` и `Ю`↔`@`.

Строка 1 содержит клавиши управляющих кодов; чтение её с маской
`FDh` на порту A возвращает такие коды:

| Bit | Клавиша        | Код |
| --- | -------------- | --- |
| 0   | TAB            | 09h |
| 1   | LF             | 0Ah |
| 2   | CR (Enter)     | 0Dh |
| 3   | DEL            | 7Fh |
| 4   | Стрелка влево  | 08h |
| 5   | Стрелка вверх  | 19h |
| 6   | Стрелка вправо | 18h |
| 7   | Стрелка вниз   | 1Ah |

Эмулятор переотображает современные клавиши PC на эту матрицу —
например, PC `F5`..`F9` покрывают АР2 / Ф-клавиши / home / СТР из
строки 0, PC `F10` переключает РУС/ЛАТ. Это удобства эмулятора, а не
аппаратные особенности РК86.

## Мониторное ПЗУ

Мониторное ПЗУ занимает диапазон F800h–FFFFh. Его таблица переходов
по адресу F800h — это стабильный ABI: вызывайте адреса слотов, а
не метки `entry_*`, поскольку внутренние точки входа могут
смещаться между ревизиями ПЗУ.

### Стек

Монитор ставит `SP = 76CFh` (сразу под видеопамятью, начинающейся
с 76D0h). Стек растёт вниз в области 7660h–76CEh. Пользовательские
программы должны использовать тот же стек либо ставить SP в
безопасный адрес ниже 7600h.

### Переменные монитора (7600h–765Fh)

| Адрес | Имя                | Размер | Значение                                           |
| ----- | ------------------ | ------ | -------------------------------------------------- |
| 7600h | `cursor_addr`      | 2      | Адрес ячейки курсора в видео-RAM                   |
| 7602h | `cursor_xy`        | 2      | `(Y,X)` — H=строка, L=колонка                      |
| 7604h | `ap2_seq`          | 1      | Индекс байта в АР2 escape-последовательности       |
| 7605h | `pressed_key`      | 1      | FFh = клавиша держится, 00h = отпущена             |
| 7606h | `ruslat_flag`      | 1      | 00h = LAT, FFh = RUS                               |
| 7609h | `keyboard_repeat`  | 2      | L = код клавиши, H = счётчик автоповтора           |
| 760Dh | `temp_sp`          | 2      | Временный слот SP, используется командами монитора |
| 7614h | `pc_storage`       | 2      | Сохранённый PC (команда G / точка останова)        |
| 7616h | `hl_storage`       | 2      | Сохранённый HL                                     |
| 7618h | `bc_storage`       | 2      | Сохранённый BC                                     |

`cursor_addr` по адресу 7600h удобен для прямой записи в видео:
`lhld 7600h`, затем запись байтов через `(HL)`. `putc` обновляет
его за вас.

`jump_to_go` по адресу 7626h — это механизм запуска
пользовательского кода. Команда `G` пишет цель в 7627h/7628h и
делает обычный `JMP 7626h`. Этот же слот служит вектором возврата
из точки останова: обработчик `RST 6` сохраняет флаги/PC, затем
возвращается через этот трамплин, так что вы можете возобновить
исполнение очередным `G`.

`ap2_seq` по адресу 7604h хранит состояние мониторной escape-
последовательности. Реализована только `ESC Y y x`: `1Bh` взводит
последовательность, следующий байт должен быть `Y`, а следующие
два — задают `row+20h`, `col+20h`. Любой другой второй байт
прерывает последовательность, и она печатается как есть.

### Команды монитора

Приглашение принимает одну букву, за которой следуют до трёх hex-
аргументов через пробелы или запятые, завершённые Enter (или `.`,
чтобы прервать и вернуться в приглашение). При ошибке разбора
эхом печатается `?`.

| Cmd | Аргументы               | Действие                                                              |
| --- | ----------------------- | --------------------------------------------------------------------- |
| `D` | `start,end`             | Дамп памяти как hex, по 16 байт в строке                              |
| `L` | `start,end`             | Список памяти как текст (печатные символы; прочие как `.`)            |

Точка останова в `G` реализована подменой байта на `RST 6` (`F7h`)
по целевому адресу; исходный байт сохраняется в `stop_addr_value`
(7625h). При срабатывании точки останова монитор сохраняет все
регистры в области 7614h–761Eh, восстанавливает байт и возвращается
к приглашению. Команда `X` печатает это сохранённое состояние.

## Видеопамять

```text
строки 0..29  ×  78 колонок в строке  =  2340 байт по адресу 76D0h

video address(y, x) = 76D0h + y*78 + x
```

Каждый байт — это **код символа**, а не битмап пикселей: ВГ75
выбирает глиф из ПЗУ знакогенератора. Стандартное текстовое окно,
используемое монитором, покрывает **колонки 8..71, строки 3..27**
(64 × 25). Его верхний-левый угол — `77C2h = 76D0h + 3*78 + 8`.

## Знакогенератор

Один байт на ячейку, **КОИ-7 Н2** — 7-битный советский стандарт,

## Лента

Программы почти всегда работают через монитор:

```asm
    lxi  h, start
    lxi  d, end
    call 0F827h        ; outblock - запись HL..DE, BC=контрольная сумма на выходе
    ...
    lxi  h, 0          ; 0 = взять адрес из заголовка блока
    call 0F824h        ; inpblock - чтение, CY установлен при ошибке контрольной суммы
```

Низкоуровневые константы, которые стоит знать:

| Значение | Назначение                                            |
| -------- | ----------------------------------------------------- |
| E6h      | Синхро-байт — также литеральный маркер в файлах       |
| 2Ah      | Константа тайминга чтения по умолчанию (≈591 мкс/бит) |
| 1Dh      | Константа тайминга записи по умолчанию (≈406 мкс/бит) |

Кадрирование битов — каждый бит пишется как **два фронта** на
выходной линии ленты. Монитор эмитирует два фронта примерно через
`1Dh` тиков для бита `0` и с другим интервалом для бита `1`;
приёмник измеряет интервалы между фронтами и восстанавливает бит.
Байты — 8 бит, MSB первым. Блок на ленте имеет такую структуру:

```text
[256 × 00h преамбула]  E6h  start_hi start_lo  end_hi end_lo
                       [байты payload]
                       E6h  sum_hi sum_lo
```

256-байтная преамбула позволяет приёмнику захватить тайминг битов
до появления первого синхро-байта `E6h`.

### DRAM-регенерация во время записи на ленту: трюк с `POP PSW`

В коде монитора по адресу `0xFC7B` (внутри routine'ы записи бита на
ленту) встречается такой цикл:

```asm
out_bit_loop2:
FC7B  F1          POP  PSW       ; «Регенерация ОЗУ» — комментарий из исходника
FC7C  05          DCR  B
FC7D  C2 7B FC    JNZ  out_bit_loop2
...
FC85  F9          SPHL           ; «Восстанавливаем SP и видео»
```

`POP PSW` здесь не работа со стеком — это **трюк для регенерации
динамической памяти**.

#### Почему RAM нужно регенерировать

РК86 на 32 КБ построен на динамической памяти К565РУ3 (16K×1, 16
микросхем). DRAM хранит бит как заряд на конденсаторе ячейки —
десятки фемтофарад, утечка через подзатвор и в подложку. Через ~2 мс
заряд деградирует настолько, что чтение становится ненадёжным.

Чтобы этого не произошло, **каждая строка DRAM должна быть
прочитана раз в ~2 мс**. У РУ3 это 128 строк (адресуются A0..A6 при
RAS-стробе). Любое обращение по адресу с битами A0..A6 = N
автоматически освежает строку N целиком (все 128 ячеек этой строки)
— это побочный эффект усилительного цикла внутри микросхемы.

#### Внутреннее устройство К565РУ3

Один чип К565РУ3 — это 16384 ячейки, физически организованные как
**128 строк × 128 столбцов**. Чтобы прочитать один бит, чип получает
адрес в две фазы:

1. **RAS** (Row Address Strobe) + 7 бит адреса строки → внутри чипа
   все 128 ячеек этой строки одновременно подтягиваются на чтение в
   линейку из 128 sense-amps (усилителей чувствительности).
   Sense-amps усиливают слабый заряд конденсаторов и записывают его
   обратно с полной амплитудой. **Это и есть акт регенерации** — все
   128 ячеек строки теперь «свежие» на следующие ~2 мс.
2. **CAS** (Column Address Strobe) + 7 бит адреса столбца → выбирает
   один из 128 уже усиленных sense-amps для подачи на выход.

Ключевой вывод: **любой RAS-цикл со строкой N автоматически
регенерирует все 128 столбцов этой строки**, даже если CAS-фаза
прочитала только один столбец. Регенерация — побочный эффект самого
факта «дёрнули RAS со строкой N», независимо от того, что было дальше.

#### Маппинг 14-битного адреса CPU на адрес строки DRAM

В РК86 CPU имеет 14 бит адреса для 16 КБ банка (плюс A14 для выбора
банка). Эти 14 бит надо подать на 7-битный адресный вход чипа в две
фазы. Делается это **мультиплексором** на плате:

- В RAS-фазе мультиплексор подаёт на чип `CPU_A0..A6` как номер
  строки.
- В CAS-фазе мультиплексор подаёт `CPU_A7..A13` как номер столбца.

Какие именно биты CPU попадают в RAS, а какие — в CAS, определяется
**разводкой платы**. Чип сам не знает «своего» битового маппинга — он
видит просто 7 бит в RAS-фазе и 7 бит в CAS-фазе.

В РК86 на RAS подаются **младшие 7 бит CPU-адреса**: `A0..A6`.

Из этого следует факт, который часто ломает интуицию:

**Строка DRAM = `CPU_A0..A6 = N`, независимо от значения `A7..A13`.**

То есть когда CPU обращается к адресу `0x76D0`:

```text
0x76D0 = 0111_0110_1101_0000
                     │└────┘
                     │  └── CPU_A0..A6 = 0x50 = 80 → строка 80 в чипе
                     └────── CPU_A7..A13 = 0x76 → столбец в чипе
```

Освежается **физическая строка 80** в микросхеме. Эта строка
содержит ячейки 128 разных «байтовых адресов» с теми же младшими
7 битами: `0x0050`, `0x00D0`, `0x0150`, `0x01D0`, …, `0x7ED0`,
`0x7FD0`. Все они теперь свежие — не только тот байт, который CPU
реально прочитал.

#### Общий RAS на оба банка

РК86 на 32 КБ — это два банка по 16 КБ, каждый из 8 чипов РУ3.
Старший CPU-адресный бит (`A14`) выбирает банк через дешифратор.

Важная деталь схемотехники РК86: **RAS-сигнал общий на все 16 чипов
обоих банков**. Различие между банками делается только коммутацией
**CAS** и шины данных через дешифратор `A14`. Это типовое решение
советских микро-ЭВМ той эпохи: даёт «бесплатную» регенерацию всей
памяти от любых обращений к любому банку.

Что это значит на практике: **любой доступ CPU или DMA к любому
адресу освежает строку с тем же `A0..A6` сразу в обоих банках**.
RAS-цикл со строкой N приходит на все 16 чипов одновременно — все
ячейки строки N во всей 32-КБ памяти регенерируются.

Без этой особенности программа в нижнем банке могла бы потерять
данные через 2 мс, если VG75 читает только верхний банк. Но
поскольку RAS общий, **VG75-DMA, читая только верхнюю половину,
обслуживает обе банки одновременно**.

#### Откуда регенерация берётся в обычном режиме

Регенерацией обычно занимается **видеоконтроллер VG75**. Через DMA
ИК57 он непрерывно читает видеопамять `0x76D0..0x7FF4` — 2340 байт
50 раз в секунду.

Любой непрерывный диапазон адресов длиной ≥128 байт **гарантированно
прокатывает `A0..A6` через все 128 значений 0..127**:

```text
addr:    0x76D0 → A0..A6 = 0x50 = 80
         0x76D1 → A0..A6 = 0x51 = 81
         ...
         0x76FF → A0..A6 = 0x7F = 127
         0x7700 → A0..A6 = 0x00 = 0
         ...
         0x774F → A0..A6 = 0x4F = 79  ← все 128 значений A0..A6 пройдены
```

2340 байт = **18 полных циклов A0..A6 за один кадр** + чуть-чуть. В
секунду — 18 × 50 = **900 регенераций каждой строки**, при
требуемом минимуме 500 (раз в 2 мс). Запас ×1.8 — с одной стороны
скромный, но достаточный с учётом того, что чтения CPU из кода и
из стека добавляют ещё RAS-циклов.

И благодаря общему RAS на оба банка эти 900 регенераций/с в секунду
получает **вся 32-КБ память**, не только видеоПЗУ.

Резюме цепочки:

1. У РУ3 ровно **128 строк** (одна строка = 128 ячеек, регенерируются
   разом RAS-циклом).
2. RAS-фаза любого обращения к чипу подаёт на адресный вход
   **`CPU_A0..A6`** как номер строки.
3. Любые **128 последовательных адресов** прокатывают `A0..A6` через
   все 128 значений → освежают все 128 строк чипа целиком.
4. **RAS общий на все 16 чипов обоих банков** → доступ в любой банк
   освежает обе банки симметрично.
5. VG75-DMA читает 2340 байт 50 раз в секунду = **18 полных проходов
   A0..A6 за кадр × 50 кадров/с = 900 регенераций/с каждой строки**.
6. Поэтому **видео-DMA = полная регенерация всех 32 КБ DRAM
   «бесплатно»**, как побочный эффект построения картинки.

Иначе говоря: **видео = бесплатная регенерация всей памяти**, потому
что строка DRAM «общая» для всего адресного пространства — `A0..A6 = N`
это одна и та же физическая строка независимо от того, в каком
128-байтном «листе» 16 КБ или в каком из двух банков ты находишься.

#### Почему регенерации нет во время записи на ленту

Запись бита делается переключением бита 0 порта C (PPI `A002h`) с
**точно отмеренной** длительностью полупериодов: 1 — короткий,
0 — длинный. Тайминг должен быть стабильным, иначе магнитофон при
чтении не разберёт.

Если в это время работает DMA, она ворует у CPU непредсказуемое
число тактов (cycle-stealing — VG75 запрашивает шину раз в строку
растра). Тайминги полупериодов поплывут, лента запишется криво.

Поэтому первое, что делает routine записи на ленту — **выключает
DMA** (записью в `0xE008` управляющего слова, гасящего канал 2).
Сразу же исчезает и автоматическая регенерация — освежать DRAM
теперь некому. Если ничего не сделать, ~через 2 мс начнут «проседать»
произвольные ячейки, прежде всего там, где код записи на ленту
лежит сам — и процессор воткнётся в мусор.

Регенерацию обязан обеспечить сам процессор, доступом к памяти из
своего кода.

#### Что делает `POP PSW` за один такт

Опкод `F1` — одна байта. Делает три полезных вещи **одной
инструкцией за 10 тактов**:

1. **Читает байт** по адресу `(SP)`. Это обращение к памяти →
   DRAM-строка с адресом, соответствующим младшим битам `SP`,
   освежается.
2. **Читает второй байт** по адресу `(SP+1)`. Освежает ещё одну
   строку.
3. **Инкрементирует SP на 2**. Это «бесплатный» автоинкремент
   указателя — не нужно отдельной `INX` или `INR`.

Восстановленные в `A` и флаги при этом — **мусор**, и здесь это
никого не волнует: значения, которые `POP PSW` затирает, не нужны.
Аккумулятор в этот момент не используется (бит для ленты уже выведен
в порт `A002h` до начала задержки).

Одна инструкция = два чтения памяти + автоадвенс. Идеальный
«memory walker» для DRAM-регенерации.

#### Как это собирается в работающую регенерацию

Цикл задержки занимает 5 байт:

```asm
out_bit_loop2:
FC7B  F1          POP  PSW       ; 10 T  — читает (SP), (SP+1); SP += 2
FC7C  05          DCR  B         ;  5 T  — счётчик задержки--
FC7D  C2 7B FC    JNZ  out_bit_loop2 ; 10 T (taken)
```

Одна итерация = **25 T-состояний ≈ 14 мкс** на 1.78 МГц. За одну
итерацию SP продвигается на 2 байта, освежая 2 строки DRAM.

Чтобы SP пробежал ≥128 разных значений A0..A6, нужно сдвинуть SP на
≥128 байт = **≥64 итерации**. 64 × 14 мкс ≈ 900 мкс — полностью
укладывается в 2 мс окно регенерации. На длинном полупериоде `B`
обычно выставлен заметно больше 64, так что весь цикл регенерации
проходится несколько раз за один бит, с большим margin'ом против
разброса CPU-таймингов и разброса ёмкости конденсаторов в DRAM.

#### Что делает `SPHL` в `FC85`

Перед заходом в задержку и выключением DMA текущий стек был сохранён
в `HL` (где-то выше в routine'е). `SPHL` после конца цикла
**восстанавливает SP** в исходное положение, чтобы дальнейший
`CALL`/`RET` продолжал работать с настоящим стеком, а не с
прошедшимся через всю память «walker'ом».

То есть SP во время задержки буквально использовался как
**указатель-итератор для регенерации** — на семантику стека на это
время плюётся, потом честно возвращается обратно через `HL`.

#### Почему именно `POP PSW`, а не что-то другое

| Инструкция          | Длина | T-states | Чтения памяти | Авто-инкремент? | Минусы                                                     |
| ------------------- | ----: | -------: | ------------: | --------------- | ---------------------------------------------------------- |
| `POP PSW`           |     1 |       10 |             2 | да (SP+=2)      | портит A, F (но они не нужны)                              |
| `POP B/D/H`         |     1 |       10 |             2 | да (SP+=2)      | портит регистр пары — нужны для счётчика/управления        |
| `MOV A,M` + `INX H` |     2 |      7+5 |             1 | да              | портит A, длиннее, медленнее, 1 строка/итерация            |
| `LDA addr`          |     3 |       13 |  1 (+2 fetch) | нет (фикс.adr)  | один и тот же адрес = одна строка, регенерация не работает |
| `LDAX D`/`LDAX B`   |     1 |        7 |             1 | нет             | нужна отдельная `INX`                                      |
| `NOP`               |     1 |        4 |             0 | —               | вообще не освежает (только fetch той же строки)            |

`POP PSW` выигрывает по совокупности: компактность, плотность
обращений к памяти, бесплатный авто-инкремент, портит регистр
которого жалко меньше всего. Другие `POP` тоже работают, но `B`,
`D`, `H` обычно заняты под счётчик / число бит / SP-копию, а
`PSW` — единственная пара, которую инженер мог себе позволить «слить».

#### Дополнительная деталь: instruction-fetch тоже регенерирует

Каждая выборка опкода — это тоже чтение памяти, тоже освежает
строку. CPU за итерацию фетчит 5 байт: `F1` по `FC7B`, `05` по
`FC7C`, `C2 7B FC` по `FC7D..FC7F`. Но это всегда **одни и те же 5
строк** (адреса кода фиксированы) — на них регенерация полная, на
остальных 123 — никакой. `POP PSW` именно для того и нужен, чтобы
**гулять по разным адресам** и тем самым прокатываться по всем
оставшимся строкам.

#### Где ещё встречается этот трюк

Идиома `POP rp` / `DCR ctr` / `JNZ` — **классика для cycle-perfect
I/O на машинах с DRAM**, где видеоконтроллер обычно занимается
регенерацией, а на время критичных по таймингу операций его
выключают. На РК86 такой код может появляться везде, где нужна
точность тайминга и не работает DMA — лента, реалтайм-звук через
бит-тогглинг A002h, точная развёртка спрайтов, синхронный обмен с
внешним устройством.

## Форматы файлов

Поля адресов — 2-байтные **big-endian**; `end_addr` — это адрес
**последнего** байта (включительно, не «после последнего»).
`payload` — это `end_addr − start_addr + 1` байт сырого
кода/данных i8080 — идентично тому, что будет в `.bin`. `checksum`
— это мониторная routine `chksum` (`F82Ah`), запущенная над
`start_addr..end_addr`, хранящаяся в big-endian.

Алгоритм контрольной суммы — **не** простая 16-битная сумма. Для
буфера из `N` байт `v[0..N-1]`:

```text
sum = 0
for i in 0..N-2:                       # каждый байт КРОМЕ последнего
    sum = (sum + v[i] + (v[i] << 8)) & 0xFFFF
# последний байт сливается только в младшую половину:
sum = (sum & 0xFF00) | ((sum + v[N-1]) & 0x00FF)
```

Эквивалентно: ведём два байта `(hi, lo)`. Для каждого байта, кроме
последнего, `lo += v[i]` и `hi += v[i] + carry_from_lo`. Для
последнего байта обновляется только `lo`, любой перенос
отбрасывается. Эта особенность (последний байт обрабатывается
отдельно, контрольная сумма НЕ коммутативна) и отличает
RK86-сумму от наивного аккумулятора при реверсе.

| Расширение     | Раскладка                                                             |
| -------------- | --------------------------------------------------------------------- |
| `.bin`         | Только сырой payload, без заголовка и трейлера.                       |
| `.rk`, `.rkr`  | `start_hi start_lo end_hi end_lo` ‖ `payload` ‖ `E6 sum_hi sum_lo`    |
| `.pki`, `.gam` | `E6 start_hi start_lo end_hi end_lo` ‖ `payload` ‖ `E6 sum_hi sum_lo` |

Так что `.pki` / `.gam` и `.rk` / `.rkr` отличаются только лидирующим
синхро-байтом: `.pki` / `.gam` повторяют синхро-байт `E6h` перед
заголовком адресов, `.rk` / `.rkr` его опускают. Хвост
`E6 sum_hi sum_lo` одинаков в обоих.

Примеры — 3-байтный payload `21 00 00` (`lxi h, 0`) по адресу
3000h, контрольная сумма `0021h`:

```text
.bin   21 00 00
.rk    30 00 30 02 | 21 00 00 | E6 00 21
.pki   E6 30 00 30 02 | 21 00 00 | E6 00 21
```

Это в точности тот формат `.rk` ленточного файла, который эмитит
плейграунд. Программы загружаются по адресу, закодированному в
заголовке файла; директива `org` в asm8 — это то, что задаёт этот
адрес.

## Программистские идиомы

### Скелет программы

```asm
    org  3000h             ; любой адрес в 0000h..75FFh
    lxi  sp, 75FFh         ; стек в верху пользовательского RAM

    lxi  h, hello
    call 0F818h            ; puts
    jmp  0F86Ch            ; назад к приглашению монитора

hello: db 'hi, world', 0Dh, 0Ah, 0
```

### Очистка экрана + печать в (row, col)

```asm
    mvi  c, 1Fh            ; очистить экран + home
    call 0F809h
    mvi  c, 1Bh            ; ESC
    call 0F809h
    mvi  c, 'Y'
    call 0F809h
    mvi  c, 3 + 20h        ; строка 3
    call 0F809h
    mvi  c, 8 + 20h        ; колонка 8
    call 0F809h
    lxi  h, msg
    call 0F818h
```

Переиспользуемый `set_cursor`, который патчит ESC-Y-шаблон на
месте (по умолчанию ничего не сохраняет) — так это делает
`docs/examples/dumped.asm`.

### Чтение одной клавиши

```asm
wait:   call 0F803h         ; getc, блокируется
        cpi  0Dh            ; Enter
        jz   done
        cpi  1Bh            ; ESC
        jz   abort
        ...
```

### Прямая запись в видео по текущему курсору

```asm
    lhld 7600h              ; HL = текущий адрес курсора
    mvi  m, 17h             ; 17h = полный блок
```

Прямая запись обходит `putc`, поэтому собственный учёт курсора
монитором останется в синхроне только если вы продолжите `putc`-
ом или escape-последовательностью `ESC Y`.

### Возврат в монитор

```asm
    jmp  0F86Ch             ; тёплый рестарт (сохраняет состояние экрана)
    ; или
    jmp  0F800h             ; холодный рестарт (реинициализирует всё)
```

Нажатие Ctrl-C во время `getc` в правильно ведущей себя программе
должно идти на `0F800h` (жёсткий сброс).

## Шпаргалка по реверсу

Паттерны, которые вы будете видеть в RK86-бинарниках снова и снова:

| Последовательность                | Значение                              |
| --------------------------------- | ------------------------------------- |
| `31 FF 75`                        | `lxi sp, 75FFh` — инициализация стека |
| `CD 18 F8`                        | `call puts`                           |
| `CD 09 F8`                        | `call putc`                           |
| `CD 03 F8`                        | `call getc`                           |
| `CD 15 F8`                        | `call hexb` — печать A как 2 hex      |
| `C3 6C F8`                        | `jmp` к приглашению монитора          |
| `0E 1F CD 09 F8`                  | очистка экрана                        |
| `0E 1B CD 09 F8 0E 59 CD 09 F8 …` | позиционирование курсора через ESC-Y  |
| `2A 00 76`                        | `lhld 7600h` — адрес курсора          |
| `3A 06 76`                        | `lda 7606h` — флаг РУС/ЛАТ            |
| Любое `CPI 03h / JZ F800h`        | «Ctrl-C возвращает в монитор»         |
| `F1 05 C2 ?? ??`                  | цикл задержки для регенерации DRAM    |

Идиома `F1 05 C2 …` декодируется как `POP PSW` / `DCR B` /
`JNZ self` и не является стековой операцией — это **DRAM-
регенератор**. Пока DMA выключен (обычно ввод-вывод ленты или
любой cycle-perfect вывод), CPU прогоняет `SP` через память,
используя автоинкремент `POP` для освежения строк DRAM
самостоятельно. Полную историю смотрите в
[DRAM-регенерация во время записи на ленту](#dram-регенерация-во-время-записи-на-ленту-трюк-с-pop-psw).

Проверки управляющих кодов на результате `getc` (`CPI 08h / 18h /
19h / 1Ah`) почти всегда говорят о обработке курсорных клавиш.

Самомодифицирующее `MVI A, nn`, за которым следует `STA ??+1`
где-то в другом месте — частая идиома для хранения малого
количества состояния прямо в коде; редактор дампа использует это,
чтобы помнить «правка половины байта в процессе» без расходования
байта RAM.

### Раскладка полей опкодов i8080 (для ручной дизассемблии)

Индекс регистра в `mov`, `mov r,r'`, `mvi`, арифметике с r:

| r   | 0   | 1   | 2   | 3   | 4   | 5   | 6      | 7   |
| --- | --- | --- | --- | --- | --- | --- | ------ | --- |
|     | B   | C   | D   | E   | H   | L   | M=(HL) | A   |

Индекс **пары регистров** в `lxi rp`, `push`/`pop`, `dad`,
`inx`/`dcx`, `ldax`/`stax`:

| rp  | 00  | 01  | 10  | 11  |
| --- | --- | --- | --- | --- |
|     | BC  | DE  | HL  | SP  |

`push`/`pop` подставляют `PSW` в слот `11` (так что `11` = SP для
`LXI`/`DAD`/`INX`/`DCX`, но PSW для `PUSH`/`POP`).

### Недокументированные опкоды и псевдонимы

i8080 оставляет несколько неиспользуемых опкодов, которые ведут
себя как NOP, но различимы для дизассемблера — их обнаружение
часто значит «этот байт на самом деле данные, а не код»:

| Байты                                           | Номинальное поведение  |
| ----------------------------------------------- | ---------------------- |
| `08h`, `10h`, `18h`, `20h`, `28h`, `30h`, `38h` | NOP (псевдоним)        |
| `CBh`                                           | JMP (псевдоним `C3h`)  |
| `D9h`                                           | RET (псевдоним `C9h`)  |
| `DDh`, `EDh`, `FDh`                             | CALL (псевдоним `CDh`) |

### Half-carry на AND (`ANA`) — нестандартный

В отличие от ADD/SUB, где half-carry вычисляется из бита 3
`(A + op)`, `ANA r` / `ANI n` устанавливает HF из бита 3 **`A | r`**
(логическое ИЛИ операнда и аккумулятора). Это реальная
особенность i8080, документированная в Intel 8080 Programmer's
Manual — код, который ветвится по HF после AND, полагается на эту
формулу, а не на результат.

### Русские строки, набранные как Latin

Старые исходники часто хранят кириллический текст, набирая его на
латинской раскладке и полагаясь на то, что диапазон 60h–7Fh
отрисует правильные глифы. Байты в hex-дампе выглядят как
бессмыслица, но красиво расшифровываются через таблицу
кириллической строки выше:

| Исходные байты (как Latin) | Отрисовка на экране    |
| -------------------------- | ---------------------- |
| `pozdrawlq` s pobedoj`     | `ПОЗДРАВЛЯЮ С ПОБЕДОЙ` |
| `prigotowxtesx`            | `ПРИГОТОВЬТЕСЬ`        |

Когда вы видите строку, почти-ASCII, но усеянную backtick'ами,
`q`, `x`, `w`, `{`, `|`, `}`, `~`, считайте, что это русский, и
переводите через таблицу 60h–7Fh.
